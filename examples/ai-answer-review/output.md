# 8つの判断材料｜AIの全面移行提案を検証する

## 01｜本当の目的

Frameworkを新しくすることではなく、特定2画面の表示遅延を、長時間停止せず、1人で保守できる形で改善することです。

## 02｜前提不足

- 遅延がFrontend、API、Database、外部Service、Networkのどこで発生しているか
- 遅い2画面で共通する処理
- Browser側の計測結果
- API Response Time
- Database Query時間
- Cache状態
- Framework移行に必要な工数
- 現行機能を再現するTest
- 段階移行の可否
- Rollback方法

## 03｜事実確認

### 事実

- 遅いのは特定2画面
- 現行FrameworkはSupport期間内
- 利用者は約500人
- 長時間停止できない
- 開発者は1人

### AI回答内の未確認断定

- Frameworkが原因
- 全面移行ですべての問題が解決する
- 既存Codeを捨てることが最善

現在の情報だけでは、いずれも確定できません。

## 04｜危機察知

- 原因を特定せず全面移行し、遅延が残る
- 既存機能の再実装漏れ
- 1人開発で移行が長期化する
- 移行期間中に旧・新両方の保守が必要になる
- 長時間停止できない条件と全面切替が衝突する
- Test不足によるRegression
- 現在の利用者500人へ影響する

## 05｜反対視点

Framework移行へ反対する立場では、遅延が2画面に限定されているため、局所的なQuery、Rendering、画像、外部通信などが原因である可能性を先に確認すべきです。

一方、現行Frameworkを維持する案だけに固定すると、将来の更新Costや技術負債を見落とす可能性があります。原因調査と中長期の更新計画は分けて考える必要があります。

## 06｜比較案

| 案 | 利点 | 主なRisk | 向く条件 |
|---|---|---|---|
| 全面作り直し | 構成を刷新できる | 工数、停止、機能漏れが大きい | 現行がSupport外で、段階移行計画と人員がある |
| 原因を計測して局所改善 | 早く影響を限定できる | 根本的技術負債は残る | 遅延が一部画面に限定される |
| 段階的Migration | Riskを分割できる | 一時的に構成が複雑になる | 新旧を機能単位で分けられる |
| 現行改善＋更新計画 | 緊急問題と将来更新を分けられる | 更新が先送りされる可能性 | 現行がSupport期間内 |

## 07｜推奨判断

最初に全面移行を決めず、次の順で進めます。

1. 遅い2画面のBrowser、API、Databaseを計測する
2. 共通原因を特定する
3. 局所改善で目標速度を満たせるか試す
4. Framework更新が必要な問題を別に一覧化する
5. 必要なら機能単位の段階Migrationを設計する

全面移行を選ぶのは、Framework固有の問題が証拠で確認され、局所改善では目的を達成できず、Test・Rollback・運用継続の条件を満たせる場合です。

## 08｜主役AIへの再指示

この判断材料を基に、表示遅延の原因を確認する計測Planを作成してください。

- Frontend Rendering、Network、API、Databaseを分ける
- 非技術者でも確認結果を記録できる表にする
- 2画面の共通点を比較する
- 局所改善、段階Migration、全面移行の判断Gateを作る
- 1人開発、利用者500人、長時間停止不可を制約にする
- 変更前後の速度とError率を比較する
- Rollback条件を明記する
